What it does

maintain-verification-skill is the upkeep loop for a skill generated by create-verification-skill — or any project-local verification skill with a feature map. It covers every feature from source and exercises every feature live, then ships at most one PR of proven corrections, or reports that nothing needed shipping, or names what blocked the pass.

The unit of rigor is the feature, not every sentence. It never edits product code: a behaviour the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it).

When to reach for it

You invoke this by typing /maintain-verification-skill — the agent won't reach for it on its own.

Your situation Reach for
The app has changed and the verification map may have rotted This skill
There is no verification skill yet create-verification-skill
A specific defect, not map drift diagnosing-bugs

Prerequisites

A project-local verification skill with launch/drive sections and a feature map, usually .cursor/skills/verify-*/. None → it stops and points at /create-verification-skill. Several → it asks which.

The feature is the unit

A map rots the moment the app changes. The pass does not terminalise every bullet. It does this:

  1. Index hygiene on the feature-map README.
  2. A read-only subagent per feature file, launched together, each returning how that user-facing feature works from source plus one live recipe. Children never drive the app and never edit files.
  3. Reconcile those recipes into as few app states as practical, and sweep recent churn for surfaces the map missed.
  4. A live pass the coordinator owns — every feature at least once — following the verification skill's own launch model.
  5. Triage: doc drift and harness gaps get fixed; product gaps get reported and stay out of the PR.

The live pass is required even when source looks clean. Three invariants hold the whole time: doctor before driving anything surprising, evidence already captured survives every cleanup, and nothing a drive started outlives that drive.

Common questions

Do I have to run /create-verification-skill first?

Yes, or already have a project-local verification skill with a feature map. This skill will not invent a target. No candidate → it stops and names /create-verification-skill.

Will it change my product code?

No. Edit scope is the verification skill's own directory: its SKILL.md, features/, and harness scripts it owns. App behaviour that is actually broken is recorded for you and kept out of the PR.

What do clean, changed, and blocked mean?

Outcome What happened
clean Every feature got source and live coverage; nothing worth shipping. No branch, no PR
changed One PR of proven doc, harness, or map corrections
blocked Coverage could not finish, or a proven fix could not ship safely. The report names exactly what blocked it

Does a feature the live pass cannot reach count as verified?

Only as verified-unreachable, and only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted. If the map omitted that prerequisite, that is drift and gets fixed.

It's working if

  • You typed /maintain-verification-skill. It did not fire because you mentioned an audit in passing.
  • Product code is untouched. The diff, if any, is inside the verification skill's directory.
  • The report is exactly one of clean, changed, or blocked.
  • A changed run is one PR, and every harness fix in it was re-driven live before it shipped.
  • Every feature file had a source read and a live drive — or is verified-unreachable with a named prerequisite.

Where it fits

maintain-verification-skill is periodic maintenance of a generated verification skill, not of the product. Reach for it when the app has moved and the map may have lied.

Its neighbour is create-verification-skill, which seeds the skill this one keeps honest. diagnosing-bugs is the move when the live pass finds a product gap rather than doc drift. ask-michal routes you over the whole set.
