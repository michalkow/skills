# Agent workflow and pstack research

Research date: 2026-11-13. Analysis and recommendations; no skills were installed or changed.

Your working pattern is outcome-led: describe a product experience or observed failure, align when necessary, then use short skill commands to move through implementation, review, and release. The largest opportunities are clearer ownership across those stages, direct proof of the delivered result, and checking the complete user experience. The two strongest new pstack capabilities are **blast-radius** and **benchmark-checklist**; most other useful mechanics fit skills you already have.

## How the agents execute the work

A common longer path is:

```text
Product intent or symptom
→ inspect code, documentation, glossary, and ADRs
→ align or research if invoked
→ spec and dependency graph of issues
→ implement vertical slices with focused checks
→ Standards and Spec review
→ optional additional bug review
→ release metadata and docs
→ commit, push, and PR handback
→ version/deploy when requested
```

The agents generally use the repository's abstractions, run focused tests/builds, and report unrelated check failures. Examples include consumer/scaffold checks for Changesets, HTTP checks for documentation hosting, and public-interface regression coverage. This is meaningful execution beyond merely drafting code. [Changesets in New App Setup](t3-thread://v2/160dcf7e-fdc2-4306-8175-8d743f07f2c2/17d0238a-231e-425e-9824-08a4cd625d4c); [Docusaurus App Integration and i18n](t3-thread://v2/160dcf7e-fdc2-4306-8175-8d743f07f2c2/45b2554e-874d-4ff7-9c1d-66f274e1d8a4); [Expose Sign-In Callback in Auth](t3-thread://v2/160dcf7e-fdc2-4306-8175-8d743f07f2c2/0bc20957-1464-44b3-99a8-225c75df89ee).

You remain the product decision-maker and sometimes the integration auditor. Agents ask about both meaningful product choices and routine implementation details. You also perform the transitions between intentional standalone stages. For example, [asking-with-docs](/Users/michalkow/Projects/skills/skills/engineering/asking-with-docs/SKILL.md) explicitly ends at shared understanding, so a thread ending there is expected behavior when you invoked that stage. It becomes a composition problem only when a larger authorized workflow fails to resume after it.

Delegation is useful when it supplies genuinely different evidence: source research, an independent review, or provider-specific telemetry access. The sampled successful workflows also show a cost: more handoffs, availability assumptions, and another opportunity for an incomplete result to be treated as delivered. This audit does not support a ranking of models or a claim that additional reviewers reliably improve product quality.

Two strengths are particularly worth preserving:

- **The agents can distinguish a controlled measurement from a live result.** In [AI Scene Narration Failure](t3-thread://v2/160dcf7e-fdc2-4306-8175-8d743f07f2c2/976e0963-01a9-4b1f-aea5-f981a2b70c03), the agent reported five controlled samples per path, a scripted model and a simulated 10 ms database round trip. Median completion fell from 69/89/114 ms to 23/23/33 ms. It explicitly said this isolated database overhead rather than live AI latency. The remaining acceptance gap is measuring the actual player-visible path, not an absence of all benchmarking.
- **A failing evaluation can prevent adoption.** In [Compare Mastra and App Knowledge](t3-thread://v2/160dcf7e-fdc2-4306-8175-8d743f07f2c2/767ed30b-79f8-42e8-bc12-76a522770214), the agent reported passing contract/backend checks but a failed 180-trial live quality baseline, and left experimental optimizations disabled. A passing implementation check and a successful product experiment were treated as different results. This audit inspected the transcript and supporting summaries; it did not rerun that evaluation.

## What to change first

This is a proposed sequence, not an implementation performed by this audit.

1. **Unify delivery ownership** in `implement-pr`, `fix-pr`, and `implement-spec`, reusing `spec-to-feature`'s current completion check. Required docs, generated output, review fixes, and release metadata must be in the final pushed result.
2. **Reconcile routine autonomy in TDD.** Preserve product decisions and explicit production authorization; remove a mandatory question for every conventional test seam.
3. **Add blast-radius for upgrades and shared-framework changes.** Prove the consequential compatibility facts with real consumer/config/runtime checks.
4. **Connect existing verification to PROJECT.md.** Exercise the important user journey, including completion and latency where relevant, before presenting the feature as done.
5. **Add benchmark-checklist to performance work.** Use it proportionately, keeping controlled results and live claims distinct.
6. **Strengthen handoff and retro with selected context/structural-prevention mechanics.** Avoid another general orchestration or reflection system.

The following upstream review explains exactly what to borrow, what already exists locally, and which defaults require adaptation.

## Recommendation

Adopt the mechanics selectively. The highest-value standalone additions are **blast-radius** and **benchmark-checklist**. Most other gains belong in the existing implementation, verification, retrospective, and handoff skills. Importing all of pstack would duplicate substantial local guidance and introduce conflicting autonomy, model, worktree, and publishing rules.

The eight recommendations below are ranked by fit to the reported problems, not by measured skill effectiveness. No controlled before/after evaluation of these adaptations has run.

### 1. Prove the delivered result, with outcome-oriented migration boundaries

**Verified upstream.** [Prove It Works](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/principle-prove-it-works/SKILL.md) requires inspection of the real artifact rather than a build, a cached representation, or a delegate's self-report. It favors a rerunnable comparison and visible evidence. [Outcome-Oriented Execution](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/principle-outcome-oriented-execution/SKILL.md) has a narrower meaning than its title suggests: during planned migrations, tolerate declared, scoped, reversible intermediate breakage, keep checks for the touched areas, and fully verify the final state. It does not itself define PR delivery completeness.

**Local evidence and overlap.** [implement-pr](/Users/michalkow/Projects/skills/skills/engineering/implement-pr/SKILL.md) and [fix-pr](/Users/michalkow/Projects/skills/skills/engineering/fix-pr/SKILL.md) commit and open a PR before calling changeset-add. [changeset-add](/Users/michalkow/Projects/skills/skills/engineering/changeset-add/SKILL.md) explicitly writes the pending file and leaves it uncommitted. That ordering is a verified source conflict consistent with the reported missing changeset. [spec-to-feature](/Users/michalkow/Projects/skills/skills/engineering/spec-to-feature/SKILL.md) now has step 12: push, match the remote PR head to local HEAD, and confirm no task-related work remains outside the PR. This is existing coverage, not a proposed new discovery.

**Recommended adaptation.** Give the outer workflow responsibility for the entire result after every nested skill returns. Produce changesets and other required artifacts before the final commit/push. At completion, compare the scoped work, local commits, remote PR head, and actual PR file list. An inner skill's legitimate “write and stop” ends that subtask, not its caller. Include review fixes and generated artifacts in the same reconciliation.

For migrations, declare acceptable temporary breakage in the development checkout, then verify the final application and delivery at the named boundary. This permission does not extend to breaking a running production system. Keep step 12's existing check and reuse it across delivery workflows; avoid a second general verification generator.

### 2. Experience First, tied to PROJECT.md and a complete user journey

**Verified upstream.** [Experience First](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/principle-experience-first/SKILL.md) requires justification for every feature, control, and option, fewer polished features, prototypes before commitment, good feedback/error states, and a tighter core loop. It treats API consumers and future maintainers as users too. [Subtract Before You Add](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/principle-subtract-before-you-add/SKILL.md) favors removal of unnecessary complexity and design for observed usage.

**Local evidence and overlap.** [m5kdev-setup-project](/Users/michalkow/Projects/skills/skills/engineering/m5kdev-setup-project/SKILL.md) already defines an outcome-focused PROJECT.md and requires inspecting actual app differences from the starter before interviewing the user. [prototype](/Users/michalkow/Projects/skills/skills/engineering/prototype/SKILL.md) already supports throwaway UI variants and visible state-model experiments. Neither needs replacement.

**Recommended adaptation.** Before building a screen or expanding an interaction, name the PROJECT.md outcome it serves and the smallest useful interaction. Compare a plain select with the proposed richer control when that is the real choice. Run the core journey after implementation, including loading, failure, empty, and completion states. For the narrative game, exercise several consecutive choice/result cycles and inspect whether the story actually advances; checking that choices regenerate only proves regeneration. Measure the waiting time as part of that journey when latency is relevant.

This addresses reported concerns about unnecessary screens, excessive controls, and narrative stasis. Review scores cannot decide whether the user needs a screen, or whether a story is satisfying. Keep genuine product judgments with the user; use prototypes and evidence to make the choice concrete.

### 3. Blast Radius for framework upgrades and cross-system changes

**Verified upstream.** [blast-radius](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/blast-radius/SKILL.md) explicitly looks beyond symbol callers: pinned dependency source and patches, runtime ordering, wire formats, DB columns, flags, and downstream readers in other languages. Its central mechanic is to identify the one or two facts a change's safety depends on and prove them with real code. Evidence ranges from a source citation through a failing script to running-app reproduction. Unproven remains unproven.

**Recommended adaptation.** For a framework upgrade, derive an affected-system map from the actual repo and authoritative migration guides: dependency/lockfile state, runtime config, env loading, deployment scripts and CI, migrations, docs/examples, starter templates, and newly generated apps. Do not turn this into a fixed checklist of irrelevant surfaces. Follow concrete edges and mark each applicable part changed, proven compatible, or unverified. A fresh generated consumer can test a different contract from the already-upgraded app.

[Local m5kdev-update](/Users/michalkow/Projects/skills/skills/engineering/m5kdev-update/SKILL.md) already resolves an exact target, reads each migration guide in the version jump, honors applied-migration metadata, and obeys install output. Blast-radius adds scrutiny of contracts the immediate diff or a guide might miss; it is not a reason to ignore those guides.

For each important edge, identify a decisive check rather than listing speculative risks. Establish the actual dependency/runtime/environment state before interpreting failures. The optional upstream arena fan-out is not needed by default and must respect the active checkout and delegation authorization.

### 4. Benchmark Checklist plus Explain the Number

**Verified upstream.** [benchmark-checklist](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/benchmark-checklist/SKILL.md) asks seven questions: the measured limiter, production-like tuning, physical limits, errors/correctness, repeatability, end-to-end relevance, and whether the work actually occurred in the timed region. Comparative measurements require at least five alternating runs per side, median and range, and a verdict of no measurable difference when spread exceeds the gap. Profiling occurs in a separate run. An untuned side, missing limiter for a claimed difference, or inability to check errors/work makes the verdict inconclusive. A user-requested ballpark has a lighter exception.

[Explain the Number](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/principle-explain-the-number/SKILL.md) adds a decision-changing result and noise floor before measurement. It also applies this skepticism to eval scores. The [hillclimb playbook](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/poteto-mode/playbooks/hillclimb.md) freezes a sensitivity-checked harness, measures each hypothesis, and reverts changes that fail the metric or regression gate.

**Local overlap and adaptation.** [diagnosing-bugs](/Users/michalkow/Projects/skills/skills/engineering/diagnosing-bugs/SKILL.md) already requires a baseline for performance work. Add the stronger measurement contract rather than a parallel debugging process. For narrative latency, measure the same user action to a usable response before and after, with workload/history, versions, concurrency, model/provider, cache conditions, success count, and completion count recorded. Report failures separately. Distinguish time to first response from time to completed usable output.

Do not infer speed from fewer functions, requests, or layers. The inspected completion thread contains five-sample controlled timing with scripted model work and a simulated database round trip. That is valid evidence about the measured overhead; it does not by itself establish live end-to-end latency. The proposed addition is stronger comparability and user-path measurement, not a claim that no benchmark existed or that the change was ineffective. Five runs are a minimum upstream recipe, not assurance of enough samples for variable LLM latency. Port Linux-specific probes such as nproc/pidstat/strace to the actual host rather than copying them onto macOS.

### 5. Sequence Verifiable Units plus Build the Lever

## Specialized candidates and approaches to defer

### Statechart: useful for selected lifecycle risks, not a default feature gate

[Statechart](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/statechart/SKILL.md) checks a TLA+ model and projects its states into reader-facing Mermaid labels. A bounded model's pass is not proof of the entire implementation.

[Arena](https://github.com/cursor/plugins/blob/6e359ce0aba9e927914d8a940510aa2ef66a8f23/pstack/skills/arena/SKILL.md) creates competing artifacts from the same brief, holds a 3–6-criterion picker rubric, isolates outputs, cross-judges, chooses one base, grafts selected strengths, and verifies the synthesis.
